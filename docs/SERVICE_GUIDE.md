# ETA 보조 사례의 코드 안내

## 요청 하나 따라가기

1. `backend/app/main.py`의 `/api/v1/routes/search`가 요청·데모 프로필을 받습니다. `build_container`가 DEMO/LIVE 공급자를 명시적으로 구성합니다.
2. `services.py`의 `RouteService.search`가 기본 경로 후보를 얻습니다. 경로 제공자 캐시와 시설 원본 캐시는 별개입니다.
3. `providers/accessibility.py`가 후보의 같은 역·정류장을 묶고 외부 정보를 병렬 조회합니다. 타임아웃/공급자 오류는 해당 항목의 UNKNOWN으로 내려갑니다.
4. `providers/seoul.py`는 엘리베이터 목록을 읽습니다. 비어 있는 캐시에 동시 요청이 들어오면 하나의 `asyncio.Task`를 기다립니다. `shield`는 대기자 한 명의 취소가 다른 요청까지 취소하지 않게 합니다.
5. `personalization.py`가 알려진 조건과 모르는 조건을 구분해 경로·경고를 만듭니다. 정보 없음이 이용 불가의 증거도, 안전하게 이용 가능하다는 증거도 아닙니다.
6. `models.py`와 `docs/openapi.yaml` → `frontend/src/api/types.ts` → `mappers.ts` → `App.tsx`: 출처·상태·조회 시각·합성 모드가 화면까지 이어집니다.

## 데이터의 의미

| 필드 | 뜻 | 이번 자료로 알 수 없는 것 |
|---|---|---|
| `exists: true` | 공급자 시설 목록에서 해당 위치를 찾음 | 지금 운행하는지, 경로 전체가 통과 가능한지 |
| `status: UNKNOWN` | 현재 이용 가능 여부 미확인 | 실제 고장·정상 여부 |
| `fetchedAt` | 목록을 받아 온 시각 | 시설이 실제로 관측된 시각 |
| `observedAt` | 운행 상태 관측 시각이 있을 때만 제공 | 목록 조회 시각을 대신 사용하지 않음 |
| `dataMode: DEMO` | 합성 경로·접근성 데모 | 실제 경로·운행 정보 |
| `dataMode: LIVE` | 외부 공급자 조회 모드 | 모든 항목이 실측·최신·완전함을 뜻하지 않음 |

`getFcElvtr` 위치 목록의 운행 관련 문자열은 실시간 상태·관측 시각 계약을 확인하지 않았으므로 현재 AVAILABLE 근거로 사용하지 않습니다. 목록은 기존과 같이 첫 1,000건을 읽습니다. 목록 밖 시설·동명이역·역 내부 실제 연결성까지 검증하지 않았습니다. 없는 행은 UNKNOWN으로 취급합니다.

## 선택 이유와 한계

경로 후보의 중복 제거만으로는 동시에 들어오는 별도 요청의 캐시 miss를 합칠 수 없습니다. 캐시를 채우는 task 자체를 공유해야 원본 요청 수를 줄일 수 있습니다. 현재는 인스턴스/이벤트 루프 하나 안의 공유입니다. 여러 프로세스 간 분산 캐시는 이번 범위가 아닙니다.

성공 결과는 기존 TTL 600초 동안 사용합니다. 실패는 캐시를 채우지 않으며 다음 요청이 다시 조회합니다. 한 대기자의 타임아웃은 공유 HTTP 요청을 취소하지 않습니다. 원본 HTTP 클라이언트의 별도 타임아웃 안에서 끝납니다. 장애가 길면 연속된 요청이 다시 원본을 호출할 수 있으며 회로 차단기나 분산 잠금을 새로 추가하지 않았습니다.

도보 환경과 실시간 교통 정보가 없으면 경고·UNKNOWN을 전달합니다. 실제 도착시간 정확도나 접근 가능한 경로의 현장 검증을 완료한 서비스는 아닙니다. 데모 인증·메모리 저장소·합성 프로필도 그대로입니다.

## 실행·공부

```sh
cd backend
uv sync --frozen --python 3.12
uv run pytest
uv run ruff check app tests
cd ../frontend
npm ci
npm test
npm run lint
npm run build
npx playwright test
```

E2E가 자체 로컬 API(18083)·프론트(4178)를 시작하므로 그 포트의 데모를 먼저 `stop`합니다. 외부 지도/장소 SDK는 테스트 대역이고 ETA API는 실제 서버입니다.

딩코딩코 5·6주차의 비동기 처리·캐시 개념을 위 공급자 호출에 연결합니다. 아래는 원문 강의 과제가 아닌 이번 구현용 보충 과제입니다.

- 빈 캐시에 8명, 채워진 캐시에 8명이 요청할 때 원본 호출 수를 예측하고 테스트합니다.
- 한 요청을 취소하고 나머지가 성공하는 이유를 `shield` 유무로 비교합니다.
- 공급자가 HTTP 200 안에 오류 코드를 반환할 때 정상 빈 목록으로 저장하면 생기는 문제를 설명합니다.
- 시설 목록은 있지만 현재 운행 시각이 없는 경우, 응답과 화면에서 어떤 값이 UNKNOWN이어야 하는지 설명합니다.
